# minecraft-rcon-mcp

*[English](README.md)*

MCP-сервер, який дає AI-асистенту (Claude, Cursor тощо) керувати живим
Minecraft-сервером через [RCON](https://minecraft.wiki/w/RCON) —
дивитись гравців онлайн, транслювати повідомлення в чат, телепортувати,
видавати предмети, міняти погоду/час, кікати, чи виконувати будь-яку
сиру vanilla/plugin-команду — замість того, щоб набирати це самому в
консолі сервера.

## Навіщо це існує

Більшість MCP-серверів дають AI-асистенту доступ до *коду* — файлової
системи, мови програмування, системи збірки. Цей дає доступ до живого
*ігрового світу*: реально інша, набагато рідша категорія MCP-інструментів,
і цікаво будувати її поверх протоколу (Source RCON), достатньо простого,
щоб реалізувати з нуля за пару сотень рядків без жодної залежності, крім
самого MCP SDK.

## Встановлення

```bash
git clone https://github.com/Faneraiy14/minecraft-rcon-mcp
cd minecraft-rcon-mcp
npm install
```

Потребує Minecraft-сервера (vanilla чи Paper/Spigot — будь-що, що
розмовляє протоколом Source RCON) з увімкненим RCON. У його
`server.properties`:

```properties
enable-rcon=true
rcon.port=25575
rcon.password=<реальний пароль — не лишай порожнім>
```

## Підключення (Claude Desktop / Claude Code)

```bash
claude mcp add minecraft-rcon-mcp -- node /абсолютний/шлях/до/minecraft-rcon-mcp/src/server.js \
  -e MC_RCON_HOST=127.0.0.1 \
  -e MC_RCON_PORT=25575 \
  -e MC_RCON_PASSWORD=<той самий пароль із server.properties>
```

`MC_RCON_HOST` типово `127.0.0.1`, `MC_RCON_PORT` типово `25575`, якщо не
задано — обов'язковий лише `MC_RCON_PASSWORD`. Пароль читається ЛИШЕ з
середовища, ніколи не приймається як параметр інструмента — параметр
MCP-інструмента приходить (чи принаймні проходить) через контекст самого
AI, а довготривалому секрету там нічого робити, коли середовище процесу
й так може його тримати.

## Інструменти

| Інструмент | Що робить |
|---|---|
| `mc_command` | Виконує будь-яку сиру vanilla/plugin-команду (провідний `/` не потрібен) — запасний варіант для всього, чого не покривають інструменти нижче |
| `mc_list_players` | Хто зараз онлайн (`/list`) |
| `mc_say` | Транслює повідомлення в чат від імені сервера (`/say`) |
| `mc_teleport` | Телепортує гравця/селектор до координат чи іншої сутності (`/tp`) |
| `mc_give` | Видає гравцю предмет (`/give`) |
| `mc_set_weather` | Встановлює погоду clear/rain/thunder, опційно на певну тривалість (`/weather`) |
| `mc_set_time` | Встановлює ігровий час за кількістю тіків чи ключовим словом на кшталт `day`/`night` (`/time set`) |
| `mc_kick` | Відключає гравця, опційно з причиною, яку той побачить (`/kick`) |

Кожен інструмент повертає `{ success, command, output }` при успішному
RCON-раунд-тріпі — `success: true` означає, що *запит дійшов до сервера й
той відповів*, а не що команда обов'язково зробила семантично те, чого
хотілось. `output` — це власний текст відповіді сервера (напр. "No player
was found" для `/give` на офлайн-гравця) — AI читає це, щоб дізнатись, що
реально сталось, так само, як людина, що читає консоль сервера.

## Як працює RCON-клієнт

[Source RCON](https://developer.valvesoftware.com/wiki/Source_RCON_Protocol)
— невеликий бінарний TCP-протокол — `src/rcon.js` реалізує його напряму,
без залежностей:

- **Формат пакета**: `[int32 length][int32 requestId][int32 type][payload][0x00][0x00]`,
  усі числа little-endian. `length` не включає сам себе.
- **Автентифікація** (`SERVERDATA_AUTH`, тип 3): надсилаєш пароль; сервер
  відповідає `SERVERDATA_AUTH_RESPONSE` (тип 2) із ТИМ САМИМ requestId
  при успіху, або `requestId: -1` при невірному паролі — це ЄДИНИЙ сигнал
  провалу автентифікації, окремого поля з текстом помилки нема.
- **Фрагментація довгих відповідей**: у протоколі нічим не позначено
  "це останній пакет відповіді" — довгий вивід `/list` чи `/help` цілком
  легітимно може прийти кількома пакетами `SERVERDATA_RESPONSE_VALUE`.
  Стандартний трюк, використаний тут: одразу після реальної команди
  надсилається ДРУГИЙ, порожній пакет `SERVERDATA_EXECCOMMAND` з
  НАСТУПНИМ requestId. Minecraft не розпізнає порожню команду, але все
  одно відлунює порожній `SERVERDATA_RESPONSE_VALUE` з ТИМ requestId — і
  оскільки відповіді приходять по порядку, поява САМЕ цього ID — надійний
  маркер "усе до цього моменту належало реальній команді".
- Реальний, живий баг, спійманий саме так: перша версія зіставляла вхідні
  пакети з очікуваннями лише за `requestId`, і НІКОЛИ не перевіряла ID
  саме термінатора — пакет-термінатор потрапляв у мертву гілку
  `_handlePacket`, тож кожен виклик команди мовчки висів до власного
  таймауту, навіть коли реальна відповідь сервера вже коректно прийшла.
  Знайдено запуском клієнта проти РЕАЛЬНОГО живого Paper-сервера (не
  мока), а не припущенням, що реалізація протоколу правильна, бо вона
  ВИГЛЯДАЄ правильною. Виправлено перевіркою `p.terminatorId` першою.
- Кожен виклик MCP-інструмента відкриває нове з'єднання, автентифікується,
  виконує ОДНУ команду й закривається — RCON у Minecraft розрахований на
  короткі адмін-підключення, не на довготривалу сесію (тому тут немає
  аналога REPL-інструментів NyxilumMcp — сенсу в них тут нема).

## Тести

```bash
MC_RCON_HOST=127.0.0.1 MC_RCON_PORT=25575 MC_RCON_PASSWORD=<пароль> npm test
```

21 перевірка: `config.mjs` (валідація env-змінних — сервер не потрібен),
`rcon.mjs` (сам протокольний клієнт проти РЕАЛЬНОГО запущеного сервера:
`list` повертає реальний вивід, невідома команда дає власний текст
помилки сервера, а не throw, невірний пароль дає `RconAuthError`, а не
зависання, недосяжний порт провалюється чисто, три послідовні команди в
одному з'єднанні не плутаються — саме той сценарій, що спіймав би баг з
termination-ID вище), `tools.mjs` (те саме через обробники інструментів,
включно з тим, що невірний пароль повертається як
`{ success: false, isAuthError: true }`, а не throw — це спіймало ДРУГИЙ
реальний баг: власні класи-нащадки `Error` у JS не виставляють `.name`
автоматично в ім'я підкласу, тож оригінальна перевірка
`err.name === 'RconAuthError'` мовчки ніколи не спрацьовувала; виправлено
явним `this.name = this.constructor.name` в базовому класі помилки й
переходом на `instanceof`), і `transport.mjs` — те саме через реальний
MCP-протокол (`StdioClientTransport` + `Client`), не лише прямі виклики
функцій.

Кожен тест, що потребує живого сервера, ПРОПУСКАЄТЬСЯ (не провалюється),
якщо `MC_RCON_HOST`/`MC_RCON_PORT`/`MC_RCON_PASSWORD` не задано — у CI
нема Minecraft-сервера під рукою, і на цьому не варто блокуватись.

## Безпека

- Пароль RCON живе лише в середовищі (див. "Підключення" вище) — ніколи
  не приймається як вхід інструмента, ніколи не логується.
- `mc_command` виконує буквально будь-який переданий рядок, без
  allowlist — це навмисний дизайн саме цього інструмента (адмін-консоль
  для ігрового світу, яким ти володієш), не недогляд. Якщо хочеш, щоб AI
  мав МЕНШЕ влади над сервером, ніж повна адмін-консоль — не підключай
  цей інструмент, або обгорни `mc_command` власним MCP-проксі, що фільтрує
  команди перед тим, як вони сюди доходять.
- Кожен RCON-виклик має timeout (типово 10с, налаштовується за викликом
  через `timeout_ms`, максимум 30с) — сервер, що перестав відповідати
  посеред команди, не підвісить викликаючий інструмент назавжди.

## Docker

```bash
docker build -t minecraft-rcon-mcp .
docker run -i --rm -e MC_RCON_HOST=<host> -e MC_RCON_PORT=25575 -e MC_RCON_PASSWORD=<password> minecraft-rcon-mcp
```

Сервер працює з MCP через stdio, тож `-i` обов'язковий. Потрібно: змінні `MC_RCON_*` твого сервера.
У конфігу MCP-клієнта: `"command": "docker"` з тими самими аргументами.
